# 🐳 Everything About Docker: Command Cheat Sheet
A comprehensive, production-ready guide to Docker commands, lifecycle management, troubleshooting, and data persistence.

## 🔍 Image Discovery & Registry Operations
Manage how you find, download, and publish Docker images to and from registries like Docker Hub.

| **Action** | **Command Syntax / Example** | **Purpose & Notes** |
|---|---|---|
| **Search Images** | `docker search <term>` | Searches for public images on Docker Hub. |
| **Filter Search** | `docker search --filter=is-official=true python` | Restricts search results to **official images** only. |
| **Pull Image** | `docker pull <image-name>:<tag>` | Downloads a specific version of an image to your local machine. |
| **Tag Image** | `docker tag <local-image>:<tag> <repo>/<image>:<new-tag>` | Creates a target alias pointer pointing to a source image. |
| **Push Image** | `docker push <repository>/<image-name>:<tag>` | Uploads your tagged local image to a remote registry. |

### 💡 Example Workflow: Tagging & Pushing
To push a local image named `my-app:latest` to your personal Docker Hub repository:

```bash
# 1. Prepare and tag the image for your repository
docker tag my-app:latest myusername/my-app:v1.0

# 2. Upload it to Docker Hub
docker push myusername/my-app:v1.0
```

## 🖼️ Local Image Management
Commands used to inspect, list, and examine locally downloaded images.

* `docker images` — Lists all locally available images, showing repository, tag, and size.
* `docker images -a` — Lists all local images, including intermediate hidden image layers.
* `docker images -q` — Returns **only** the numerical Image IDs (excellent for automation scripts).
* `docker inspect <image_id_or_name>` — Returns deep, low-level configuration data in **JSON** format.

### 🛠️ Why use Inspect?
* **Debugging:** View environment variables, open ports, and layout schemas.
* **Troubleshooting:** Identify underlying architecture misconfigurations.
* **Automation:** Parse JSON values seamlessly inside Bash or Python scripts.

## 🏗️ Build & Run Architecture
The core workflow tools used to compile your source blueprints into functional application containers.

### 1. Build Phase
The `docker build` command compiles a customized Docker image using instructions written inside a local `Dockerfile`.
* **Context:** Docker processes instructions sequentially (`FROM`, `COPY`, `RUN`), generating isolated, cacheable intermediate layers.

```bash
docker build -t my-app:latest .
```
* `-t`: Assigns a human-readable repository name and version tag (`my-app:latest`).
* `.`: Informs Docker that the current active directory contains the context files and `Dockerfile`.

### 2. Execution Phase
The `docker run` command reads a target image blueprint, spins up hardware isolation spaces, and starts your process.

```bash
docker run -d -p 8080:80 --name my-nginx nginx
```
* `-d`: **Detached Mode**. Runs the container safely inside the background process loop.
* `-p 8080:80`: **Port Mapping**. Maps host machine port `8080` to the container's internal port `80`.
* `--name`: Assigns an explicit, custom string identifier (`my-nginx`) to replace random auto-generated strings.

## 🚦 Container Status & Diagnostics
Commands for observing active runtime workloads and extracting system crash reports.

### Listing Workloads
* `docker ps` — Displays a real-time status matrix of **currently running** containers.
* `docker ps -a` — Displays **all** containers (including stopped, crashed, and exited instances).
* `docker ps -q` — Returns only unique container numeric IDs.

### Error Analysis & Investigation
* `docker inspect <container_id>` — Returns low-level system states, internal IP structures, and runtime configuration matrices.
* `docker logs <container_id>` — Fetches stdout/stderr streams generated by the container's core process engine.

#### ⚙️ Common Log Flag Combinations
| **Flag** | **Alternative** | **Practical Application** |
|---|---|---|
| `-f` | `--follow` | Streams active production print statements live onto your screen. |
| `--tail N` | — | Limits output history matrix to the last `N` execution lines. |
| `-t` | `--timestamps` | Prepends structural RFC dates to every individual line event. |
| `--since` | `--until` | Limits time tracking evaluations (e.g., `--since 1h`). |

## 💾 Storage Strategies: Volumes & Mounts
Docker provides three distinct isolation styles to persist your application data outside of transient container lifecycles.

```text
       [ HOST MACHINE STATE FILE SYSTEM ]
 ┌──────────────────────────────────────────────┐
 │  ┌─────────────────┐    ┌─────────────────┐  │
 │  │  Bind Mounts    │    │ Docker Volumes  │  │
 │  │ (/host/path)    │    │(/var/lib/docker)│  │
 │  └────────┬────────┘    └────────┬────────┘  │
 └───────────┼──────────────────────┼───────────┘
             ▼                      ▼
 ┌───────────┴──────────────────────┴───────────┐
 │             [ ISOLATED CONTAINER ]           │
 └──────────────────────────────────────────────┘
```

### Storage Type Breakdown
* **Anonymous Volumes:** Docker provisions a volume with a randomized tracking ID hash. Good for temporary caches.
  ```bash
  docker run -v /data busybox
  ```
* **Named Volumes:** Explicitly defined storage blocks managed completely by Docker. Best for database files.
  ```bash
  docker volume create mydata
  docker run -v mydata:/data busybox
  # Alternative modern syntax:
  docker run --mount type=volume,source=mydata,target=/data busybox
  ```
* **Bind Mounts:** Direct mappings linking an explicit directory on your host workstation to the container runtime. Excellent for live code hot-reloads.
  ```bash
  docker run -v /host/path:/container/path busybox
  ```
* **Tmpfs Mounts:** Non-persistent, ultra-fast memory storage spaces that exist purely inside system RAM.
  ```bash
  docker run --mount type=tmpfs,target=/data busybox
  ```

### Architectural Tradeoffs
| **Feature** | **Volumes** | **Bind Mounts** |
|---|---|---|
| **Storage Location** | Managed by Docker (`/var/lib/docker/volumes/`) | Explicit user-defined paths on Host OS |
| **Lifecycle** | Independent of active container execution cycles | Tied directly to host hardware states |
| **Portability** | Highly portable across different OS configurations | Difficult; relies heavily on host path directory structures |
| **Backup Ease** | Native integration via direct Docker API access | Requires custom external host file backup utilities |
| **Performance** | Highly optimized for virtualized host patterns | Dependent completely on underlying host drive types |

## 🧹 System Housekeeping & Garbage Collection
Over time, build layers and stopped assets consume massive amounts of disk space. Use these commands to reclaim storage.

* `docker image prune` — Safely deletes unreferenced, dangling intermediate image layers.
* `docker volume prune` — Destroys unattached storage volumes that are no longer tied to any container.
* `docker system prune` — A massive unified cleanup tool that wipes out:
  * All stopped containers.
  * All unused networks.
  * All dangling build images.
  * *(Note: This does **not** delete volumes by default to protect database data).*
